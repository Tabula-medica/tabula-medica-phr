# Permission Copy Parity Audit

**Purpose:** Apple App Privacy questionnaire rejections most often come from a mismatch between (a) the `Info.plist` `NSXxxUsageDescription` string the OS shows in the system permission sheet, (b) the in-app pre-prompt copy, (c) the App Store listing's privacy section, and (d) the published privacy policy. Even subtle differences ("we record" vs "we may record") can trigger a 5.1.1 rejection.

This document is the single source of truth. **Update this file first, then propagate.**

**Status legend:**
- ✅ verified in repo, all four locations match
- ⚠️ canonical string set, but one or more locations are not yet implemented in the codebase or live web pages
- ❌ mismatch between locations — must fix before submission

**Last verified:** 2026-04-18 against `capacitor.config.ts`, `.local/deliverables/app-store-submission.md`, `client/src/**`. Privacy policy URL `https://tabulamedica.health/privacy` not yet audited (see Action Items).

## Android Health Connect parity

Android equivalents go in `android/app/src/main/AndroidManifest.xml` (generated by `npx cap add android`) and in the Play Console Data Safety form.

| Permission | Manifest entry | Data Safety category | Status |
| --- | --- | --- | --- |
| Read steps, heart rate, vitals | `<uses-permission android:name="android.permission.health.READ_*" />` per category | Health & Fitness → Health info → Read | ⚠️ pending build |
| Write vitals | `<uses-permission android:name="android.permission.health.WRITE_*" />` per category | Health & Fitness → Health info → Write | ⚠️ pending build |
| Record audio | `RECORD_AUDIO` | Audio files | ⚠️ pending build |
| Camera | `CAMERA` | Photos and videos | ⚠️ pending build |
| Read media images | `READ_MEDIA_IMAGES` (API 33+) | Photos and videos | ⚠️ pending build |
| Use biometric | `USE_BIOMETRIC` | n/a | ⚠️ pending build |
| Coarse location | `ACCESS_COARSE_LOCATION` | Location → Approximate | ⚠️ pending build |

**Note:** Android's user-facing Health Connect prompt uses Google's standard copy, not ours, so Manifest <-> Play Store parity is the one we control. Per-category Health Connect rationale strings we *do* control should mirror the iOS strings above.
