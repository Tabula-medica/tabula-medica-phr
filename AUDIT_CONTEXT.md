## 3. Where I most want fresh eyes

In priority order. Skim everything else.

### 3.1 PHI encryption boundary (HIGHEST CONCERN)
- `server/compliance/compliance-enforcement.ts` and `server/compliance-routes.ts` — does the enforcement actually run on every PHI-touching route, or are there bypass paths?
- Anywhere PHI columns are read/written without going through the envelope encryption helper
- The `PHI_ENCRYPTION_SALT_V2` secret is listed as missing — is the v1→v2 rotation path actually implemented anywhere, or is it aspirational?
- Logs: any chance PHI is leaking into `console.log` / structured logs? Specifically search for `patient.firstName`, `patient.dob`, `medication.name` being logged.

### 3.2 Care Access subsystem isolation (the "zero PHI" promise)
The Care Access subsystem (`/care/*` routes, `client/src/pages/care-*.tsx`, plus its server routes) is marketed as zero-PHI — it serves uninsured patients who haven't created accounts. Verify:
- No accidental PHI bleed from the authenticated session into Care Access endpoints
- The QR share flow (`care-share-qr.tsx`) — what's actually in the QR payload? Is it a token that resolves to PHI server-side, or PHI in the URL?
- `CARE_BRIDGE_SECRET` — what does it gate, and is the gate strict?

### 3.3 RTL/i18n correctness
Heavy use of Tailwind logical properties (`me-2`, `ms-2`, `ps-4`, `text-start`, `text-end`) instead of physical (`mr-2`, `ml-2`, `pl-4`, `text-left`, `text-right`). This is intentional for Arabic/Hebrew support. **Audit:** grep for any `mr-`, `ml-`, `pr-`, `pl-`, `text-left`, `text-right` that slipped through — each one is a future RTL bug.

### 3.4 Smoke test coverage vs. real risk
`/admin/smoke-test` has 12 sections that the App Store reviewer walks. Question for the auditor: do those 12 sections actually exercise the high-risk paths (PHI write, HealthKit read, FHIR import, Care Access QR generation), or do they over-cover the safe surface (login, dashboard, settings) and under-cover the risky one? Compare `client/src/pages/admin-smoke-test.tsx` SECTIONS array to the real route map in `client/src/App.tsx`.

### 3.5 (Lower priority) `.github/workflows/`
Two workflows: `pr-security-check.yml` and `soc2-deploy.yml`. Do they actually gate merges, or are they advisory? Are the SOC2 controls in `soc2-deploy.yml` real or theatrical?

## 4. Things this codebase does differently from typical patterns

Flagging these so the auditor doesn't waste time investigating them as bugs.

1. **`shared/schema.ts` is 22,000 lines.** This is intentional, not a smell — Tabula Medica models the full FHIR R4 surface plus subscription/billing/care-access/audit tables in one file per the fullstack-js skill convention. Don't recommend splitting it; the cross-table type inference depends on the single-file structure.

2. **Hundreds of `*-routes.ts` files in `server/`.** Same reason — one route file per domain. There's no monolithic router. `server/routes.ts` (if it exists) just composes them.

3. **`/admin/smoke-test` ships in production.** This is deliberate. It's how App Store reviewers walk the app, and it's how investors demo it. It's gated by admin role on the server side; the page itself is fine to expose at the URL level. Do not flag as "remove debug page from prod".

4. **`<LegalFooter />` uses a hardcoded route-suppression list** rather than a layout-level config. Reason: there's no shared layout component; pages render their own roots. The single global insertion point in `App.tsx` was the alternative to touching 100+ pages, and the suppression list is the trade-off. Acceptable until/unless the layout is consolidated.

5. **`localStorage` is heavily relied on** for: smoke-test results (`smoke-test-v1`), smoke-test run state (`smoke-test-run-v1`), review prompt safety gates (`review-prompt-state-v1`), pre-prompt seen flags (`pre-prompt-shown:*:v1`), permission telemetry (`permission-telemetry-v1`). Clearing site data resets the App Store reviewer experience — that's intended (it makes the demo idempotent).

6. **Toast `action` prop must be a JSX `<ToastAction>`, not a plain object.** Found the hard way while writing `client/src/lib/review-prompt.ts`. If the auditor sees what looks like overly verbose toast invocations, that's why.

7. **Capacitor is configured for bundled-asset (offline-first) mode**, not server-mode. The mobile app ships the entire built `dist/public/` inside the IPA/AAB. This is correct for HIPAA (no in-flight PHI from a remote server hosting the SPA shell) and correct for the "uninsured patient with no data plan" use case. Don't flag as "why isn't this loading from the server like a normal Capacitor app".

8. **Sign in with Apple is implemented via Auth0 social connection**, not native ASAuthorization. Apple Guideline 4.8 is satisfied because Auth0 handles the OAuth dance with Apple's servers and the user sees Apple's own consent sheet. We don't need the native `Sign in with Apple` button SDK. `server/replitAuth.ts` forwards `connection=apple` to Auth0 and Auth0 does the rest.

9. **Two encryption salt env vars** — `PHI_ENCRYPTION_SALT` (active) and `PHI_ENCRYPTION_SALT_V2` (listed as missing). The v2 is for an upcoming rotation but the rotation code path may or may not be live. Worth flagging in 3.1.

10. **`app.json` and `capacitor.config.ts` coexist.** `app.json` is Expo-style config carried over from an earlier wrap attempt; `capacitor.config.ts` is the live config. Both have permission strings — both have been canonicalized. The `app.json` is kept around because some asset-generation tooling reads it; should probably be retired post-Mac-build.
